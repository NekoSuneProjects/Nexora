# Authenticator MFA setup (preview)

Set MFA_ENCRYPTION_KEY to exactly 64 hexadecimal characters generated by a CSPRNG and supplied through a secrets manager before allowing enrollment. Persist this key across restarts and across all API replicas. Losing the encryption key makes existing authenticator secrets inaccessible.

1. Sign in normally using username and password.
2. Call POST /api/v1/auth/mfa/enroll with the Bearer session. It returns an RFC 4648 Base32 secret. This secret is presented once for enrollment and is not saved in plaintext to PostgreSQL.
3. Add the secret to an authenticator using TOTP SHA1, six digits, 30-second period.
4. POST /api/v1/auth/mfa/confirm with {"code":"123456"} using a current authenticator code.
5. Subsequent POST /api/v1/auth/login requests include mfa_code with password.

The web login form now allows an optional six-digit authenticator code.

Security limitations: no recovery codes, no WebAuthn, no re-authentication for enrolling the second factor, no attested device enrollment, and no independent review. MFA setup/recovery is not production-ready. Avoid enabling this for irreplaceable accounts without a separate reviewed recovery process.
Confirmation now returns eight high-entropy, single-use recovery codes. They are stored as SHA-256 hashes and must be copied offline immediately. Supply recovery_code alongside username and password when the authenticator is unavailable. Each recovery code is deleted atomically upon successful verification; it cannot be reused. This is an initial recovery option, not a complete identity-verified lost-account recovery policy. Password changes, step-up authentication, session revocation on recovery, abuse tests and independent review remain necessary.
